# Benchmark methodology

A run prepares one seeded dataset per size and reuses it across all index variants. Benchmark generation truncates the selected sandbox tables with identity reset after confirmation. Index changes are transactional, PostgreSQL plans are based on refreshed statistics, and the benchmark restores the original index definitions when it finishes. The sandbox retains data from the last generated size. Selected queries and parameter overrides are held fixed within a scenario comparison. The optional randomized ordering is seeded.

- **Client latency** starts immediately before JDBC execution, consumes all result rows using bounded fetch batches, and stops before rollback or commit. It includes PostgreSQL execution, JDBC, and result transfer. Warm-up samples are discarded.
- **PostgreSQL timing and plans** are collected on a separate execution using EXPLAIN JSON with ANALYZE, BUFFERS, WAL and VERBOSE. Planning and execution times are reported independently of client timings.
- **Statistics** include minimum, maximum, mean, median, sample standard deviation, P95 and P99. Percentiles use Commons Math's default percentile estimator. Small samples produce noisy estimates.
- **Throughput** is measured samples divided by the elapsed measured batch, including transaction cleanup, scheduler effects, and sequence restoration for write experiments. Concurrent measurements use separate connections.
- **Buffers and WAL** are taken from PostgreSQL plan JSON. A shared buffer read is a load into PostgreSQL shared buffers and may be serviced from the operating system cache. I/O, CPU and memory usage are only considered measured if the instrumentation collected them. The studio does not currently collect operating system counters.
- **Plan nodes** show estimates, actual rows and inclusive time per loop. Do not sum parent and child times. Total statement time comes from the EXPLAIN envelope.
- **Storage** sums ordinary user-table storage and attached index sizes across the sandbox. Candidate index build time covers explicit CREATE INDEX statements for that configuration and excludes ANALYZE. Rebuilding baseline indexes can warm caches.
- **Write experiments** use one connection and roll back each execution. Accessible PostgreSQL sequence values are restored between runs. Locks, WAL, page changes, cache effects and external effects of installed functions may persist outside transaction state. Use controlled SQL and isolated practice data.
- **Load tests** use separate concurrent connections, staggered ramp-up, then a fixed measurement window. Throughput uses successful operations completed within the window. Percentiles use a reservoir of up to 8,192 timings. The error rate includes SQL failures, with separate counts for SQLSTATE deadlocks and lock timeouts. The peak lock wait is sampled about twice per second. Rollback mode can still advance sequences. Committed mode changes sandbox data.

These experiments are warm-cache or unspecified-cache comparisons. PostgreSQL statistics, OS scheduling, and ambient resource contention can affect measurements. Historical comparisons match labels and dataset sizes. Compare seeds, queries, parameters, versions, type fixtures and host conditions before drawing conclusions across runs.
